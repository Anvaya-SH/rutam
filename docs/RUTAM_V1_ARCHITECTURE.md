# RUTAM v1 implemented architecture

Audit date: 2026-11-16. This document describes inspected code, not the original product vision.

## Actual execution

`RUTAMModelFactory.create_model` assembles `RUTAMForCausalLM`, a `BackboneProtocol` implementation, `GraphMemoryBridge`, neural query head, relation-aware graph encoder, selector, bounded traversal, gated cross-attention fusion, write head and a memory controller. With no supplied backbone it constructs **SyntheticBackbone**. That is an explicit test architecture, not LiquidAI weights.

`RUTAMForCausalLM.forward` calls `execute_rutam_forward`: capture/validate one GraphState snapshot, mask inaccessible/expired/retracted nodes, embed tokens and execute initial backbone layers. By default, each token's causal prefix produces a query, chunked candidate scoring ranks persisted node embeddings, a bounded neighborhood is extracted, and only that induced subgraph enters relational message passing. Fusion uses the selected encoded states; remaining layers and the LM projection produce logits, and shifted labels produce loss. Diagnostic query/traversal objects describe the last prefix; fused hidden states cover the full sequence. Layer signature inspection avoids catching and hiding internal TypeError failures. Query/fusion integration currently occurs after the later of configured query and fusion indices; distinct earlier query/later fusion interception remains limited.

Node features absent from graph state are zero tensors with `has_embedding=False`; trainable projections do not imply semantic understanding. The default hard-selector path uses `NodeProjection.forward_for_selection` on persisted node embeddings in bounded chunks, then runs relation embeddings/message passing only on top-k seeds plus a deterministic, two-hop neighborhood capped by `max_sparse_nodes` (64 by default). `rutam_model.sparse_max_hops` controls that local expansion; the general traversal default remains three hops for API compatibility. Soft selection, full graph attention, and the explicit `sparse_selection_enabled=False` compatibility path still use dense encoding.

This bounds relational encoder work, not all retrieval work: every visible candidate is still scored for each causal token prefix, and neighborhood/subgraph extraction reads the edge list. Candidate ranking and top-k indices run without autograd. The selected-score recomputation is differentiable to the query, selector scorer, and candidate projection if a training objective consumes those scores; the LM loss does not consume selected scores directly. LM gradients do reach selected-subgraph encoder states through fusion, the continuous query gate, and traversal's continuous path-scoring context when present. No gradient differentiates the discrete candidate ordering itself. Sparse-first execution is a relational-encoding bound, not a sublinear or constant-time graph retrieval claim.

The bridge caches detached inference work only in eval/no-grad, keyed by graph/version, tensor identity and mutation versions, encoder parameter identity and versions, and visibility. Refresh and reload synchronize with the Graph lock. Training recomputes encodings for independent backward passes. Generation uses an explicit captured graph snapshot across decoding steps. Generation recomputes the prefix; a verified LFM3 KV-cache integration is absent. Optional recurrent execution also runs per prefix to avoid future leakage and is expensive. CPU float32 graph modules are the tested contract; arbitrary GPU/bfloat16 support is not established.

## Graph state and persistence

`Graph` owns stable integer node IDs and typed edges with stable edge identifiers, metadata and retired-ID sets. Tensor rows are separate from persistent IDs. Node records carry source/evidence references, confidence, verification status, validity window, record version, scope and permissions. Edge records include identity, confidence, status, validity and version. Metadata serializes JSON lists for permissions and ISO timezone-aware timestamps. Empty graphs are valid; no factual seed memories are generated.

Public graph mutation, tensor snapshot and same-Graph save methods share a per-graph reentrant lock. Transactions lock that same graph during publication, including direct commit calls. Across Graph instances and processes, the storage API compares the writer's observed manifest generation under a POSIX advisory publication lock and rejects stale saves. It does not merge conflicting mutations or provide a distributed database.

`GraphStorage.save` writes and fsyncs immutable `snapshot-<uuid>/graph.safetensors`, `graph.json`, and a generation manifest. It fsyncs the generation and parent, then publishes `graph.manifest.json` with atomic replacement. The manifest binds checksums, sizes, graph/schema version, snapshot identity and payload directory. Load follows that generation and binds its snapshot ID to the returned graph. Save compares that expected generation under the publication lock; stale writers raise `SnapshotConflictError`. Transactions carry their base generation into commit, and rollback checks the generation it observed before republishing an older complete snapshot. An unbound graph writing into an existing directory conflicts by default; pass `expected_generation=...` when the caller has observed the active ID, or `unconditional=True` for explicit last-writer-wins behavior. Schema-v1 fixed-file snapshots remain loadable and are preserved into an immutable generation before the first upgraded save. Interrupted, uncommitted generations are ignored rather than automatically promoted.

Root `graph.safetensors` and `graph.json` are independently written compatibility exports, not hard links to new generations. Ordinary failed saves attempt to restore these exports to the committed generation. **Consumers must use GraphStorage.load or the manifest and locking protocol. Independently reading root payload files is not a transactional API, particularly across a process crash.** Older snapshots may still have hard-linked exports until a successful save replaces them. If the manifest is replaced but directory fsync fails, `SnapshotPublicationError` reports that publication occurred but durability is uncertain; callers must not assume rollback. POSIX advisory locks/local-filesystem fsync are the supported filesystem contract. Generation cleanup is manual; snapshots are not secure deletion. Schema remains v1 with optional additive fields and explicit legacy loading, not an arbitrary schema migration engine.

Safetensors is a tensor format, not a graph database. `graph.json` carries non-tensor records. The repository uses `graph.manifest.json`, not an invented `graph_meta.jsonl` format. No active `graph.rag` backend was identified. Checkpoint manager saves model tensors to `model.safetensors`, graph snapshots separately and optional optimizer tensors separately. Bundle neural weights are under `weights/model.safetensors`; the public scripts do not demonstrate a separate trained `library.safetensors` deployment. Attachment checks source/target overlap and writes a uniquely named sibling manifest (returned as `manifest_path`), not through a checkpoint symlink; repeated attachments retain those manifests. Original foundation files were not written.

## Writes and trust boundaries

The neural write head returns structured MemoryProposal objects without committing them. Public transactions require an explicit trusted AuthorizationContext containing `commit` permission for mutations. They check allowed proposal/target scopes, node write permissions, version if supplied, baseline validator acceptance and persistent replay IDs; custom validators can add restrictions, not bypass baseline validation. Changes are staged on an isolated working Graph with auto-save disabled until explicit commit, then persisted and published under the graph lock. Pre-publication save failures leave the live graph unchanged; storage conflicts return an uncommitted `CommitResult`; post-publication fsync failures synchronize the live state and report committed-with-durability-warning. Post-commit audit/archive failures likewise report successful commit with a maintenance error. Archives are independent GraphStorage snapshots.

Supported transaction operations are NO_OP, CREATE_NODE/ADD_NODE, UPDATE_NODE/UPDATE, PROPOSE_LINK/LINK, DELETE_NODE/DELETE and DELETE_LINK. Structured content/node type/scope/relation fields are honored; embeddings-only proposals store empty content rather than invented facts. Unsupported MERGE/SUPERSEDE/REQUEST_VALIDATION actions fail explicitly at this transaction boundary. Their enum values remain for compatibility with experimental code. The learned operation head retains its configured class count; adding runtime operation IDs does not mean learned delete competence. The 10,000-entry replay ledger fails closed at capacity and is retained in graph metadata. Deleting active memory does not erase historical snapshots.

Validation checks provenance categories, confidence, dimensions, targets, duplicates and version conflicts. Evidence references are recorded and credential-like text is filtered; an evidence string does not prove external truth. The API caller supplies trusted authorization; model-generated provenance cannot grant commit permission.

## Verification limits

The genuine graph neural computation is connected to the **synthetic/protocol backbone** path and has executable causal/gradient/round-trip proofs. A real LFM3 global-attention interception, tokenizer compatibility, cache contract, dtype/backend behavior and learned graph-memory QA remain unverified. `rutam-attach-lfm3` inspects checkpoint headers/attaches files; it does not establish real forward compatibility. Without a supported model-specific bridge and real checkpoint tests this repository cannot be called a verified LFM3-native model.

No distillation, instruction tuning, large training run, external RAG service or new agent framework was introduced. Existing recurrent/training modules remain outside the architecture acceptance claims.
